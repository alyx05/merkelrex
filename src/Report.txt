## TASK 1: Data Aggregation & OHLC Engine

### i. Conceptual Explanation

The OHLC engine aggregates raw order book entries — loaded from `20200601.csv` — into per-day financial summaries for a chosen product. Each entry in the order book carries a timestamp, price, and amount. The engine's role is to group these by date and extract the first price (open), last price (close), maximum price (high), and minimum price (low) within each daily window. This is done separately for asks and bids, since the two sides of the market have independent price dynamics. The `OHLCEntry` struct (defined in `OHLCEntry.h`) acts as the output container, holding the date string alongside the four price values.

The user interaction in `handleOHLC()` prompts for a product string such as `ETH/BTC`, then optionally a start and end date in `YYYY/MM/DD` format. If no date range is specified, the engine returns the full dataset. The results are printed to the console in a tab-separated table with column headers for both the ask and bid sides.

### ii. Implementation Logic & Pseudocode

The `getOHLC` method on the `OrderBook` class filters entries by type and product, applies date boundary checks against the date prefix of each timestamp, sorts the remaining entries chronologically, then groups them into a `std::map<std::string, std::vector<OrderBookEntry>>` keyed by date string. The map's natural ordering ensures dates are processed in ascending sequence without any manual sort. For each date bucket, the open is taken from the first entry, the close from the last, and the high and low by scanning the full set.

```
FUNCTION getOHLC(type, product, startDate, endDate) RETURNS vector<OHLCEntry>

    INITIALIZE filteredOrders AS empty vector

    FOR EACH order IN orderBook DO
        IF order.type != type OR order.product != product THEN SKIP

        SET dateStr = first 10 characters of order.timestamp
        IF startDate not empty AND dateStr < startDate THEN SKIP
        IF endDate not empty AND dateStr > endDate THEN SKIP

        APPEND order TO filteredOrders
    END FOR

    IF filteredOrders IS EMPTY THEN RETURN empty list

    SORT filteredOrders BY timestamp ASCENDING

    INITIALIZE ordersByDate AS std::map<string, vector<OrderBookEntry>>
    FOR EACH order IN filteredOrders DO
        APPEND order TO ordersByDate[date prefix of order.timestamp]
    END FOR

    INITIALIZE ohlcList AS empty vector
    FOR EACH (date, dayOrders) IN ordersByDate DO
        SET open  = dayOrders.front().price
        SET close = dayOrders.back().price
        SET high  = max price across dayOrders
        SET low   = min price across dayOrders
        APPEND OHLCEntry{date, open, high, low, close} TO ohlcList
    END FOR

    RETURN ohlcList
END FUNCTION
```

## TASK 2: Session Security & Authentication

### i. Conceptual Explanation

The platform enforces authentication before any trading functionality is accessible. On startup, `init()` enters a blocking `while (!isLoggedIn)` loop that presents the auth menu (`showAuthMenu()`), and the main trading menu is only reached after `isLoggedIn` is set to `true` by a successful login.

Three paths are available: registration, login, and password reset.

**Registration:** The user provides a full name, email, and password. A duplicate check queries `USERS_REGISTER.CSV` line by line and compares the stored name and email fields (columns 1 and 2). If no match is found, a 10-digit numeric username is generated by concatenating ten calls to `rand() % 10`. The plaintext password is never stored — it is passed through `std::hash<std::string>` and only the resulting `size_t` digest is written to file. A sign-up bonus of 5000 USDT is recorded in `USERS_WALLET.CSV` and also injected into the active in-memory wallet via `wallet.insertCurrency`.

**Login:** The supplied username is looked up in `USERS_REGISTER.CSV`. If found, the entered password is hashed at runtime and compared to the stored hash value. On a match, `isLoggedIn` is set to `true` and `currentUserProfile` is populated.

**Password Reset:** The user provides their username and registered email. If both match the stored record, a new password is accepted, hashed, and the entire `USERS_REGISTER.CSV` is rewritten with the updated hash for that entry.

### ii. Implementation Logic & Pseudocode

```
FUNCTION handleRegister()
    INPUT fullName, email

    IF userExists(fullName, email) THEN
        PRINT "Account already exists."
        RETURN
    END IF

    INPUT password

    SET username = ""
    FOR i = 1 TO 10 DO
        username += to_string(rand() % 10)
    END FOR

    SET passwordHash = std::hash<std::string>{}(password)

    WRITE username, fullName, email, passwordHash TO USERS_REGISTER.CSV
    WRITE username, 5000.0 TO USERS_WALLET.CSV

    wallet.insertCurrency("USDT", 5000.0)
    PRINT "Your username is: " + username
END FUNCTION

FUNCTION handleLogin() RETURNS bool
    INPUT username, password

    IF loadUser(username, outUser) THEN
        IF std::hash<std::string>{}(password) == outUser.passwordHash THEN
            isLoggedIn = true
            currentUserProfile = outUser
            RETURN true
        END IF
    END IF

    PRINT "Invalid credentials."
    RETURN false
END FUNCTION

FUNCTION handlePasswordReset()
    INPUT username, email

    IF loadUser(username, outUser) AND outUser.email == email THEN
        INPUT newPassword
        SET newHash = std::hash<std::string>{}(newPassword)
        REWRITE USERS_REGISTER.CSV replacing this user's hash with newHash
    ELSE
        PRINT "Username and email do not match."
    END IF
END FUNCTION
```

## TASK 3: Wallet & Transaction History

### i. Conceptual Explanation

Two CSV files persist financial state across sessions. `USERS_WALLET.CSV` records currency balances per user, and `USERS_TRADING.CSV` is an append-only ledger of all transactions. Both files store the username as the first column, allowing multi-user isolation when parsing.

The `TransactionEntry` struct (defined in `TransactionEntry.h`) defines the schema: username, timestamp, product, type (`deposit`, `withdraw`, `asksale`, `bidsale`), price, amount, and total value. Each row in `USERS_TRADING.CSV` follows this layout.

**Deposits and withdrawals** are handled by `handleWalletAdjustments()`, which reads a currency token and amount, calls `wallet.insertCurrency` or `wallet.removeCurrency` respectively, and logs the action with type `deposit` or `withdraw` before calling `syncWalletFile()`.

**Recent transactions** (`showRecentTransactions()`) reads the full `USERS_TRADING.CSV`, filters rows where column 0 matches the current user's username, stores them in a vector, then iterates backwards from the last element, printing up to five entries with their timestamp, product, type, price, amount, and total value.

**Activity statistics** (`showUserActivityStats()`) performs the same file scan but accumulates counts of ask and bid sales, and a running total of capital spent on bids (using the total value column). An optional product filter narrows the results.

### ii. Implementation Logic & Pseudocode

```
FUNCTION showRecentTransactions()
    OPEN USERS_TRADING.CSV

    INITIALIZE userTrades AS empty vector of strings
    FOR EACH line IN file DO
        IF tokenise(line)[0] == currentUser.username THEN
            APPEND line TO userTrades
        END IF
    END FOR

    SET count = 0
    FOR i = userTrades.size()-1 DOWN TO 0 DO
        IF count >= 5 THEN BREAK
        PRINT parsed columns: timestamp, product, type, price, amount, totalValue
        count++
    END FOR
END FUNCTION

FUNCTION showUserActivityStats()
    INPUT productFilter (optional)

    OPEN USERS_TRADING.CSV
    SET askCount = 0, bidCount = 0, totalSpent = 0.0

    FOR EACH line IN file DO
        SET tokens = tokenise(line)
        IF tokens[0] != currentUser.username THEN SKIP
        IF productFilter not empty AND tokens[2] != productFilter THEN SKIP

        IF tokens[3] == "asksale" THEN askCount++
        IF tokens[3] == "bidsale" THEN bidCount++; totalSpent += stod(tokens[6])
    END FOR

    PRINT askCount, bidCount, totalSpent
END FUNCTION
```

## TASK 4: Trading Simulation Engine

### i. Conceptual Explanation

`runTradingSimulation()` generates at least 50 synthetic orders across all known products. For each product, it runs two loops — five bid orders and five ask orders — using prices derived from the real historical order book data.

**i. Price calculation:** The simulation calls `OrderBook::getLowPrice` and `OrderBook::getHighPrice` on the historical asks for each product to establish a realistic price floor and ceiling. A random multiplier `(rand() % 100) / 100.0` is applied to interpolate a price within that range: `simulatedPrice = lowPrice + (factor × (highPrice - lowPrice))`. A small random amount between 0.1 and 2.1 is similarly generated. Fallback bounds of 10.0 and 100.0 are applied if the order book returns zero (empty product slot). This approach avoids fabricating unrealistic prices while requiring no prediction model.

**ii. Date gap handling:** The historical CSV data is timestamped in 2020. The simulation resolves the gap to 2026 by calling `std::chrono::system_clock::now()` at runtime and formatting the result with `std::put_time` into a `YYYY/MM/DD HH:MM:SS` string (via `getSystemTimestamp()`). All generated `OrderBookEntry` objects use this real system timestamp, so they naturally carry 2026 dates and are correctly captured by the OHLC engine when queried for current-year data.

**iii. Insufficient balance handling:** Before executing each bid, `wallet.containsCurrency(quoteCurrency, totalCost)` is called. If the wallet lacks sufficient funds, the order is skipped with a diagnostic message `[SIM SKIPPED] Insufficient <currency> to place Bid on <product>` and the loop continues to the next iteration. The same guard on the ask side checks that enough of the base currency is held. This prevents negative wallet states without aborting the simulation.

### ii. Implementation Logic & Pseudocode

```
FUNCTION runTradingSimulation()
    SET simTime = getSystemTimestamp()   // real 2026 timestamp
    SET products = orderBook.getKnownProducts()

    FOR EACH product IN products DO
        SET baseCurrency  = product.split('/')[0]
        SET quoteCurrency = product.split('/')[1]

        SET historicalAsks = orderBook.getOrders(ask, product, earliestTime)
        SET lowPrice  = OrderBook::getLowPrice(historicalAsks)   // fallback: 10.0
        SET highPrice = OrderBook::getHighPrice(historicalAsks)  // fallback: 100.0

        // 5 Bid orders
        FOR i = 1 TO 5 DO
            SET factor = (rand() % 100) / 100.0
            SET simPrice  = lowPrice + factor * (highPrice - lowPrice)
            SET simAmount = 0.1 + (rand() % 10) / 5.0
            SET totalCost = simPrice * simAmount

            IF NOT wallet.containsCurrency(quoteCurrency, totalCost) THEN
                PRINT "[SIM SKIPPED] Insufficient " + quoteCurrency
                CONTINUE
            END IF

            CREATE bidOrder{simPrice, simAmount, simTime, product, bidsale, username}
            wallet.processSale(bidOrder)
            orderBook.insertOrder(bidOrder)
            logTransaction("bidsale", product, simPrice, simAmount)
        END FOR

        // 5 Ask orders — mirror structure, checking baseCurrency balance
        ...
    END FOR

    syncWalletFile()
    PRINT transactions generated count
END FUNCTION
```

## TASK 5: Input Validation & Menu Design

### i. Conceptual Explanation

All user input is read through `std::getline` rather than `std::cin >>`. The direct extraction operator leaves the input stream in a failed state on non-integer input and does not consume the newline, causing subsequent `getline` calls to return empty strings. By reading a full line into a `std::string` first, the stream is always consumed cleanly regardless of what the user types.

Integer conversion is then attempted with `std::stoi` inside a `try-catch(...)` block. If `stoi` throws (on alphabetic input, empty strings, or overflow), the catch block silently resets the option to `0`, which `processUserOption` treats as an invalid choice and prints a rejection message. This means no crash path exists from malformed menu input.

The same pattern is applied to the authentication loop in `init()`: the auth choice is read via `getline` and parsed with `try-catch`, so entering letters at the login prompt produces the "Invalid choice" message and loops cleanly.

Numeric inputs for amounts in `handleWalletAdjustments` use `std::stod` in a `try-catch` block, returning immediately on bad input without modifying the wallet. The menu itself lists options `1` through `11` only, with all template placeholder options removed.

### ii. Implementation Logic & Pseudocode

```
FUNCTION getUserOption() RETURNS int
    PRINT "Type in 1-11"
    READ rawLine VIA std::getline

    SET option = 0
    TRY
        option = std::stoi(rawLine)
    CATCH (any exception)
        option = 0   // treated as invalid by processUserOption
    END TRY

    RETURN option
END FUNCTION

FUNCTION processUserOption(option)
    IF option == 0 THEN PRINT "Invalid choice. Choose 1-11."
    IF option == 1 THEN printHelp()
    IF option == 2 THEN printMarketStats()
    ...
    IF option == 11 THEN runTradingSimulation()
END FUNCTION
```
